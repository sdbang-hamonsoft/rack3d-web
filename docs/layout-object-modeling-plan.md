# 배치 오브젝트 3D 모델링 — 제작 방식 제안 (2026-09-03)

사용자 요청: 랙 안 서버처럼 "육면체 + 앞뒤 사진"이 아니라, 아래 6종은 실제 3D 모델을 만들어 쓰자.
항온항습기 · 벽걸이 온습도 센서 · UPS · 누수 감지 센서 · 배터리 랙 · 가스 소화 설비.

**이 문서는 제안이다. 확정 전에는 코드를 건드리지 않는다.**

## 0. 지금 무엇이 어떻게 그려지고 있나

두 종류를 섞어 말하기 쉬워서 먼저 구분한다.

| | 랙 **안**의 IT 장비 | ZONE 바닥의 **배치 오브젝트** |
|---|---|---|
| 데이터 | `/zones/{id}/u-maps` 의 `RackAsset` | `/layouts/zones/{id}/layout` 의 `LayoutObject` |
| 현재 표현 | GLB 3종(`dell-poweredge-r760`·`hpe-proliant-dl360-gen11`·`cisco-ucs-c240-m7`) + 앞/뒤 실사진 텍스처(E17) | **팔레트 색 단색 박스 + 모서리 선 + 이름표** (`LayoutObjectMesh`) |
| 코드 | `src/App.tsx` `ServerMesh` 근처 | `src/App.tsx:627` `LayoutObjectMesh` |

요청한 6종은 **전부 아래쪽(배치 오브젝트)** 이다. 즉 "앞뒤 사진 붙인 육면체"를 고치는 게 아니라,
E18 ④ 에서 "3D 모델은 확보하지 않는다(대강 구분만 되면 된다)"고 정했던 결정을 뒤집는 일이다.

## 1. 결론 — Blender 헤드리스 스크립트로 직접 모델링한다

이미지→3D AI(Meshy·Tripo·Rodin·Higgsfield 류)는 이 8종에 **쓰지 않는다.**

### 1-1. 먼저 정정 — 기존 "서버 모델 3종"은 상세 모델이 아니다

이 문서 초안에서 "Blender 본이 1.05MB 로 가장 작다"고 Tripo 42.7MB 와 나란히 비교했는데
**그 비교는 틀렸다.** `scripts/dev/glb-stats.mjs` 로 실측한 결과다.

| 파일 | 삼각형 | 텍스처 이미지 | 크기 |
|---|---|---|---|
| `cisco-ucs-c240-m7.glb` | **18** | 5장 | 1030 KB |
| `dell-poweredge-r760.glb` | **16** | 4장 | 392 KB |
| `hpe-proliant-dl360-gen11.glb` | **16** | 4장 | 663 KB |
| `rack-42u.glb` | 2,676 | 0장 | 215 KB |

삼각형 16~18개 = **상자 하나**다. 서버 3종은 사용자가 말한 그대로 "육면체에 앞뒤 이미지를
붙인 것"이고, 1MB 의 대부분이 지오메트리가 아니라 텍스처다. Tripo 42.7MB 와 크기만 견주는 것은
서로 다른 물건을 비교하는 것이었다. 아래 근거는 그 정정을 반영한 것이다.

### 1-2. AI 생성을 쓰지 않는 이유

- **실측 비교 (같은 조건, 텍스처 없는 실제 메시):** 이번에 만든 배터리 랙은
  **2,324 tris · 125 KB · 텍스처 0장**이다. Tripo 의 Cisco 서버는 42.7 MB 였다.
  대역폭은 이 프로젝트에서 이미 한 번 문제가 됐다 — 정리 전 `dist/` 59MB 중 미사용 GLB 가 47MB.
- **8종 다 원시 도형 조합이다.** 캐비닛(항온항습기·UPS)·프레임+모듈 반복(배터리 랙)·
  실린더 다발(가스 소화 설비)·소형 벽걸이 상자(온습도·누수)·돔(화재)·판넬(도어).
  이미지→3D AI 가 이기는 영역은 유기적 형상이고, 반복·격자가 있는 상자는 오히려 약하다.
- **축·치수·원점을 우리가 정해야 한다.** 1타일 풋프린트(0.5m), Y-up, +Z 정면, 바닥 원점.
  AI 출력물은 어차피 Blender 로 들여와 리스케일·리오리엔트·데시메이트해야 한다.
- **재현·수정 비용.** 스크립트는 git 에 남고 치수 한 줄 고쳐 다시 뽑는다. 사진이 도착하면
  비율만 맞추면 된다. AI 생성은 매 시도가 크레딧이고 "조금만 낮게" 같은 수정이 안 된다.

AI 는 **참고 이미지/컨셉 시안** 용도로는 값싸다. 최종 에셋 파이프라인에 넣을 이유가 없을 뿐이다.

### 1-3. Blender MCP 가 아니라 헤드리스 스크립트다

기존 `blender/cisco-ucs-c240-m7.blend` 는 Blender MCP(GUI 애드온, 포트 9876)로 만들었다.
그 방식은 **이 환경에서 쓸 수 없고, 쓸 이유도 없다.**

- 맥미니(`Denniss-Mac-mini.local`)에 Blender 가 아예 없었다 → `brew install --cask blender`
  로 설치했다(5.2.1). 포트 9876 도 닫혀 있었다.
- MCP 애드온은 Blender 창이 떠 있어야 하고, 결과가 `.blend` 바이너리로만 남아 diff 도
  재생성도 안 된다. 9.2MB 짜리 `.blend` 가 저장소에 들어와 있는 것이 그 결과다.
- 헤드리스 스크립트는 사람 손이 필요 없고, git 에 남고, CI 에서도 돈다.

```
/Applications/Blender.app/Contents/MacOS/Blender --background --factory-startup \
  --python blender/objects/battery_rack.py -- public/models/objects/battery-rack.glb
```

### 1-4. 검증된 파이프라인 (2026-09-03)

| 파일 | 역할 |
|---|---|
| `blender/objects/_common.py` | 박스·실린더·베벨·재질 헬퍼, 재질별 병합, 규약 검사(`report`) |
| `blender/objects/<type>.py` | 타입 1종의 형상 정의 |
| `blender/objects/_preview.py` | **익스포트한 GLB 를 다시 읽어** 3면 프리뷰 렌더 |
| `scripts/dev/glb-stats.mjs` | 배포될 GLB 의 삼각형·프리미티브·크기·바운딩박스 실측 |

세 가지가 실제로 물렸다.

1. **재질별 병합은 필수다.** 병합 전 오브젝트 60개가 프리미티브 60개로 나갔다. 병합하면 5개다.
   ZONE 에 배치 오브젝트가 20개면 1,200 드로우콜과 100 드로우콜의 차이다.
2. **삼각형 수는 익스포트 후에 세야 한다.** Blender 쪽 `report()` 는 모디파이어 적용 전이라
   948 을 셌는데 실제 GLB 는 2,324 였다(베벨이 3배로 불린다). 예산 판정은 `glb-stats.mjs` 값으로 한다.
3. **재질 최종 조정은 앱 안에서 해야 한다.** 프리뷰 조명을 세게 잡았더니 base color 0.115 의
   어두운 전면 패널이 은색으로 떠 보였다. 재질 버그가 아니라 노출 문제였다.
   실제 씬은 노출이 높고 ACES 톤매핑이 걸려 있어(§3) **같은 함정이 그대로 있다.**
   프리뷰는 형상 검수용이고, 색·금속감은 `npm run dev` 로 씬에서 확인한다.

## 2. 만들 때 지킬 규격

- **1 오브젝트 = 1 타일.** FMS `zone_layout_object` 에 width/depth 컬럼이 없다(§11-31 ②).
  실물 항온항습기가 600mm보다 커도 **여기서 물리 치수를 지어내지 않는다.** 모델은 1타일 안에 들어와야 한다.
- **높이는 `LAYOUT_OBJECT_HEIGHTS_M` 유지**(CRAC 2.0 · UPS 1.6 · WATER 0.2 · SENSOR 0.3 · GAS 0.3).
  낮게 잡은 이유가 "랙 사이 시야를 가리지 않게"이므로 모델링하면서 키우지 않는다.
- **팔레트 색은 유지.** 텍스처 없이 단색 + 형상으로 간다(§3 스타일 A).
- **이름표가 살아 있어야 한다.** 이 오브젝트는 "색 + 이름표"가 정보 전부라 `occlude` 를 일부러 뺐다.
  모델이 커지면 옆 칸 이름표를 가린다 — 모델 적용 후 ZONE 10 진입 기본 카메라에서 재확인한다.
- **예산: 1종당 3k tris 이하, 텍스처 이미지 0장, GLB 150KB 이하.** 8종 합 1.2MB 미만이 목표.
  (초안의 "60KB 이하"는 실측 전 추정이었다. 배터리 랙 실측이 2,324 tris · 125KB 다 —
  텍스처가 없어도 위치·법선 float32 가 삼각형당 50바이트대를 먹는다. 더 줄여야 하면
  베벨 세그먼트를 줄이거나 Draco 를 켠다. Draco 는 지금 꺼져 있다(`GLTF_USE_DRACO = false`).)
- **모르는 type 은 지금처럼 회색 박스로 흘려보낸다.** FMS 가 종류를 늘려도 깨지면 안 된다(현행 계약).

## 3. 스타일 — 레퍼런스 확정 (2026-09-03, 사용자 제시)

사용자가 레퍼런스 시트를 보냈다: `artifacts/reference/fms-object-3d-guide.jpg`
("FMS 통합 관리 객체 3D 표준 규격 가이드"). **§3 의 스타일 선택은 이것으로 끝났다 — B(실사풍 PBR)다.**
§1 의 제작 방식(Blender) 은 그대로다. 레퍼런스는 "무엇을 만들지"를 정하지 "어떻게 만들지"를 바꾸지 않는다.

⚠️ **이 시트 자체가 AI 생성물이다.** 한글 라벨이 깨져 있다("김치 판엘"·"다끈한 판엘"·"비터리 진벤"·
"코쿡관의"·"진자 잠금 장치"). 하단 "PBR 머티리얼 사양" 표도 **실측 규격이 아니라 그림의 일부**다.
형상·색감·디테일 밀도의 **아트 디렉션 참고로만** 쓰고, 수치를 사양으로 인용하지 않는다.
metallic 0.7~0.8 / roughness 0.3 대의 도장 금속 느낌이라는 방향성 정도만 가져간다.

### 시트에서 읽히는 대상 8종

| 시트 항목 | FMS type | 형상 요약 |
|---|---|---|
| 항온항습기 | `CRAC` | 세로 캐비닛 2연 + 상단 원형 팬 그릴 + 전면 LCD + 측면 타공 패널 |
| 배터리 랙 | **없음(§4)** | 프레임 + 모듈 12단 반복 |
| UPS | `UPS` | 캐비닛 + LCD + LED 컬럼, 도어 열림 상태로 내부 셀 노출 |
| 온습도 센서 | `SENSOR` | 소형 벽걸이 상자 + 표시창 |
| 누수 센서 | `WATER` | 소형 벽걸이 상자 + 바닥 감지 케이블 |
| 가스 소화 설비 | `GAS` | 적색 실린더 4본 + 매니폴드 배관 + 압력계 |
| 화재센서 | `FIRE` | 천장형 돔 + LED |
| 도어 | `DOOR` | 판넬 + 개폐 각도 |

요청받은 6종보다 2종(화재센서·도어)이 더 들어 있다. 같은 스타일로 함께 만드는 편이 낫다 —
한 화면에 섞이는데 둘만 색 박스로 남으면 그게 더 눈에 띈다.

### 실사풍으로 가면서 지켜야 하는 것

1. **팔레트 색은 받침대로 옮긴다.** 시트도 각 객체를 회색 받침 위에 올려놨다. 그 받침을
   타입별 팔레트 색(`LAYOUT_OBJECT_COLORS`)으로 칠하면 2D 에디터 대응이 살아 있으면서
   본체는 실사로 갈 수 있다. 받침만 `meshBasicMaterial`+`toneMapped={false}` 로 두면
   ACES 톤매핑이 팔레트 색을 미는 문제도 그대로 피한다. **이게 §3-A 와 B 의 절충이고 권장안이다.**
2. **텍스처 이미지를 쓰지 않는다.** 이 룩은 재질 5~10개(도장 금속·플라스틱·유리·적색 도장·고무)
   분할로 낸다. 이미지 텍스처를 넣기 시작하면 §1 의 용량 논거가 무너진다.
   목표: 1종당 100~200KB, 8종 합 1.5MB 이하(현행 모델 4개 합이 2.3MB다).
3. **화면 속 숫자를 모델링하지 않는다.** 시트에는 `22.5°C / 51.2%`, `PRESSURE: 42 Bar`,
   `PWR: ON` 이 찍혀 있다. FMS 는 이 객체들의 텔레메트리를 주지 않는다 —
   **글자는 실값이어야 한다**는 규칙(C6)에 걸린다. 표시창은 읽히지 않는 어두운 유리면으로 둔다.
4. **누수 감지 케이블은 만들지 않는다.** 시트의 노란 케이블은 바닥을 여러 타일에 걸쳐 지나간다.
   FMS 에 케이블 경로 데이터가 없고 점유는 1타일이다. 지어내면 없는 배선을 그리는 것이다.
   본체(벽걸이 감지기)만 만든다.

## 4. 막힌 것 — 배터리 랙은 FMS 팔레트에 없다

FMS 팔레트 12종은 `RACK CRAC UPS POWER FIRE WATER SENSOR CCTV DOOR GATE GAS SEISMIC` 다.
레퍼런스 8종 중 7종은 매핑된다(항온항습기=CRAC, 온습도=SENSOR, 누수=WATER, 가스소화=GAS,
화재센서=FIRE, 도어=DOOR, UPS=UPS). **배터리 랙만 대응 타입이 없다.** 셋 중 하나를 정해야 한다.

1. ✅ **확정 (2026-09-03, 사용자)** — FMS 에 `BATTERY` 타입 신설 요청 (2D 에디터 팔레트·색 포함)
2. ~~`UPS` 또는 `POWER` 로 배치하고 배터리 랙 전용 모델은 두지 않는다~~
3. ~~라벨 문자열로 구분한다~~ → 사용자 자유 입력이라 조용히 어긋난다

### 확정에 따라 갈라지는 일

`BATTERY` 는 **FMS 쪽 변경이 있어야 생긴다** — 팔레트 추가·색 배정·2D 에디터 노출·
`zone_layout_object.type` 허용값. rack3d 혼자 만들 수 없으므로 netis-fms 에 별건으로 요청한다.

그동안 rack3d 는 막히지 않는다. `LayoutObject.type` 이 유니온이 아니라 `string` 이고
모르는 값은 회색 박스로 흘려보내는 계약이라(`objectColor`/`objectHeightM`),
**모델을 미리 만들어 두고 FMS 가 `BATTERY` 를 내보내기 시작하면 자동으로 붙는다.**
FMS 를 기다리느라 모델링을 미룰 이유가 없다.

FMS 에 요청할 내용:
- `type` 팔레트에 `BATTERY` 추가 (기존 12종 → 13종)
- 2D 에디터 색 배정. rack3d 는 FMS 색을 그대로 따라간다 —
  기존 12색과 구분되는 값이면 되고, `UPS`(#7B1FA2)·`POWER`(#C2185B) 와 헷갈리지 않을 것
- 기존 데이터 마이그레이션은 불필요(신규 배치부터 쓰면 된다)

## 4-B. 치수 재검토가 필요하다 (실사풍의 부작용)

현재 높이(`LAYOUT_OBJECT_HEIGHTS_M`)는 "색 박스로 대강 구분"을 전제로 정한 값이라
실사 모델과 맞지 않는 것이 있다.

| type | 현행 높이 | 레퍼런스 실물감 | 판단 |
|---|---|---|---|
| `CRAC` | 2.0 | 세로 캐비닛 ~2m | 유지 |
| `UPS` | 1.6 | 캐비닛 ~1.8m | 유지 가능 |
| `GAS` | **0.3** | 실린더 다발 ~1.5m | **충돌** — 0.3m 실린더는 우스꽝스럽다 |
| `WATER` | 0.2 | 벽걸이 감지기 | 벽걸이인데 바닥 0.2m 에 놓인다 |
| `SENSOR` | 0.3 | 벽걸이 감지기 | 같은 문제 |
| `FIRE` | 0.3 | 천장형 돔 | 천장인데 바닥에 놓인다 |

낮게 잡은 이유는 "랙 사이 시야를 가리지 않게" 였다. 실사 모델을 넣으면 이 이유와 정면으로 부딪힌다.

✅ **확정 (2026-09-03, 사용자)** — 벽걸이·천장형 3종(`WATER`·`SENSOR`·`FIRE`)은
**기둥 없이 그대로 띄운다.** 해당 타일 위 1.2~1.5m 에 떠 있는 것으로 그린다.

초안은 "얇은 기둥/브래킷 위에 올린다"였는데 사용자가 기둥 없이 띄우자고 했고, 그 편이 낫다 —
**FMS 에 없는 설치물(기둥·브래킷)을 지어내지 않아도 된다.** 기둥을 그리면 현장에 없는 구조물을
있는 것처럼 말하는 것이고, 벽에 붙은 것을 바닥 기둥으로 옮겨 그리는 것도 마찬가지다.
공중에 떠 있는 편이 "이 위치에 벽/천장 설치되어 있다"는 사실만 말하고 멈춘다.

`GAS` 는 0.3m → 약 1.5m 로 올린다(실린더 다발).

## 6. 회사에 요청할 자료 — 사진보다 기종명이 먼저다

사용자 질문(2026-09-03): "앞뒤면 이미지가 있으면 돼? 회사에 달라고 할까?"

**앞뒤 이미지로는 안 된다.** 랙 안 서버에 쓰는 "육면체 + 앞뒤 사진"(E17) 은 서버가
랙에 꽂혀 앞·뒤 두 면만 보이기 때문에 성립한다. 이 8종은 **바닥에 놓여 사방에서 보이고**
카메라가 공중에서 도는 씬이라, 평면에 사진을 붙이면 옆에서 볼 때 종잇장으로 보인다.

그래도 자료는 받을 가치가 있다 — **텍스처가 아니라 모델링 레퍼런스로** 쓴다. 우선순위 순:

1. **제조사 + 모델명** (가장 값이 크다). 예: `Vertiv Liebert PDX`, `APC Symmetra PX`.
   기종명만 있으면 제조사 공개 도면·제품 사진으로 형상과 비율을 내가 맞출 수 있다.
   사진 10장보다 모델명 한 줄이 낫다.
2. **정면·측면 사진 각 1장.** 장비 전체가 프레임에 들어오고, 되도록 정면에서 수직으로.
   비스듬한 사진은 비율 추정이 어긋난다. 후면은 있으면 좋고 없어도 된다(잘 안 보인다).
3. **대략 높이·폭** (줄자 수준으로 충분). FMS 가 물리 치수를 관리하지 않으므로
   `LAYOUT_OBJECT_HEIGHTS_M` 을 우리가 정해야 하는데(§4-B), 그 근거가 된다.

⚠️ 받은 사진을 **텍스처로 굽지 않는다.** 조명·그림자가 구워진 사진을 재질에 넣으면
씬 조명과 이중으로 겹쳐 어색해지고 용량도 커진다. 형상·색·패널 배치를 눈으로 보고 옮긴다.

## 7. 항온항습기 (CRAC) — 사양 확정 (2026-09-03)

출처: 사용자 제공 `artifacts/reference/FMS-관리오브젝트-3D모델링.xlsx` 시트 "항온항습기".
3면도·아이소메트릭을 `artifacts/reference/precision-ac-3view.png`·`precision-ac-iso.png` 로 뽑아 뒀다.

기준 기종: **STULZ (독일) CyberAir 3 PRO DX**

| 항목 | 값 |
|---|---|
| 바운딩 박스 | 1200 x 890 x 1980 mm |
| BaseColor | `#E2E6E8` 본체 / `#2A2E33` 하부 프레임·베젤 |
| Metallic | 0.8 섀시 / 0.1 유리·베젤 |
| Roughness | 0.3 섀시 / 0.1 유리 / 0.6 필터 |

제작 결과: `public/models/objects/precision-ac.glb` — **724 tris · 114 KB · 텍스처 0장**.

### 7-1. 1타일에 안 들어간다 — 넘기기로 했다

폭 1.2m 는 타일(600mm) **2칸**, 깊이 0.89m 는 **1.5칸**이다. §2 의 "1타일" 규약과 정면으로 부딪힌다.

줄이는 쪽은 답이 아니다. 폭을 0.5m 로 맞추면 비율이 무너져 사물함처럼 보이고, 비율을 지킨 채
축소하면 높이가 0.83m 로 내려가 2m 랙 옆에서 알아볼 수 없다.

**넘기기로 한다. 이미 그렇게 하고 있기 때문이다** — `rack-42u.glb` 실측이
`0.600(W) x 2.000(H) x 1.000(D)` 로, 깊이 1.0m 는 600mm 타일의 **1.67배**다.
랙은 진작부터 앞뒤 타일을 넘어 서 있었고, 그게 옳다고 이미 판단한 셈이다.

`_common.report(limit=..., limit_reason=...)` 가 종별 상한을 올릴 수 있게 하되 **근거를 강제한다.**
근거 없이 넘긴 상한은 다음 사람이 "원래 그런가 보다" 하고 더 넘긴다.

⚠️ 부작용: 이웃 타일에 오브젝트가 있으면 겹쳐 보인다. FMS 가 점유를 1타일로만 관리하므로
(`UNIQUE(zone,x,z)`, width/depth 컬럼 없음) rack3d 가 막을 방법이 없다. 실데이터에서 겹침이
실제로 보이면 그때 FMS 에 점유 크기를 요청한다 — 지금 지어내지 않는다.

### 7-2. 사양서에서 **빼기로** 한 것

1. **LCD 실시간 온/습도 표시** (사양서: "22.5°C / 50%RH 텍스처 표시").
   FMS 는 이 오브젝트의 텔레메트리를 주지 않는다. ZONE 온습도 시리즈(E19 B4)는 존 센서값이지
   이 장비의 값이 아니다 — 장비 화면에 띄우면 남의 값을 이 장비 값처럼 보이게 한다.
   → 화면은 꺼진 유리(`#0E1114`, roughness 0.1).
2. **상태 LED 정상 Green / 경보 Red 전환.** 같은 이유로 상태 데이터가 없다.
   전부 초록으로 켜 두면 "전부 정상"이라고 말하는 것이고 그건 지어내기다(C6).
   → 렌즈 형상만, 발광 없음. **배터리 랙 1차본의 초록 LED 도 같은 이유로 걷어내야 한다.**
3. **Normal Map 으로 타공 그릴 표현.** 노멀맵은 텍스처 이미지고, 텍스처 0장 규약(§2)과 부딪힌다.
   → 실제 슬랫 지오메트리로 깎았다. 2개 밴드 19장에 tris 증가분이 미미하다(전체 724).
   화면에서 밋밋해 보이면 그때 노멀맵을 재검토한다.
4. **유지보수 여유공간(Clearance Zone) 투명 박스.** FMS 에 그 데이터가 없고,
   1타일 점유와 겹쳐 오히려 배치를 오독하게 만든다.

### 7-3. 엑셀의 Three.js 생성 코드는 쓰지 않는다

시트 1 뒤쪽에 `GLTFExporter` 로 7종을 뽑는 코드가 있는데, 각 객체가 **`BoxGeometry` 하나**다.
그건 지금 화면에 나오는 색 박스와 같은 물건이라 이 작업의 출발점이 될 수 없다.

### 7-4. 어긋난 것 — 엑셀의 "도어 센서" vs 팔레트의 `DOOR`

엑셀은 **도어 센서(Door Contact Sensor)** 를 말한다 — 문틀에 붙는 30x80x20mm 마그네틱 접점이고,
`Sensor_Main`(문틀)과 `Sensor_Magnet`(문) 분리를 요구한다.
그런데 FMS 팔레트의 `DOOR` 는 높이 2.1m 로 잡혀 있어 **문 자체**로 보인다.
첫 레퍼런스 시트(`fms-object-3d-guide.jpg`)도 문 판넬을 그렸다. 어느 쪽인지 확인이 필요하다.

## 8. 배치 미리보기로 확인한 것 (2026-09-03)

`blender/objects/_scene_preview.py` 가 만든 모델들을 **실제 씬 규격(600mm 타일)** 위에
기존 `rack-42u.glb` 와 함께 세운다. 프리뷰 1개짜리 렌더는 "무엇처럼 생겼나"만 답하지만,
이건 **랙 옆에서 크기가 맞나, 타일을 넘긴 모델이 이웃을 침범하나**에 답한다.

실측 결과 (타일 = 600mm):

| 모델 | 점유 | 높이 |
|---|---|---|
| `rack-42u` (기존) | 1.00 x **1.67** 칸 | 2.00 m |
| 항온항습기 | **2.00** x 1.56 칸 | 1.98 m |
| UPS | 1.00 x 1.48 칸 | 1.80 m |
| 배터리 랙 | 0.77 x 0.74 칸 | 1.55 m |
| 가스 소화 설비 | **2.00** x 0.53 칸 | 1.42 m |

- **키는 서로 맞는다.** 항온항습기 1.98m 가 랙 2.00m 와 나란히 서서 어색하지 않다.
- **1칸에 온전히 들어가는 것은 배터리 랙뿐이다.** 나머지는 전부 넘긴다 —
  그리고 **기존 랙이 이미 1.67칸을 쓰고 있었다.** 넘침은 이번에 생긴 문제가 아니다.
- ⚠️ **미해결**: 항온항습기·가스 소화 설비가 가로 2칸이라 옆 칸에 오브젝트가 있으면 겹친다.
  실배치도에 그런 경우가 있는지 확인 중(사용자에게 질의). 있으면 FMS 에 점유 크기를 요청한다.

## 9. 남은 4종은 "크기"부터 정해야 한다

온습도·누수·화재·도어 센서는 실물이 작다. 엑셀 기준 온습도 120x120x30mm,
누수 150x100x40mm, 도어 접점 30x80x20mm. 화재 감지기도 지름 100mm 대다.

**실측대로 만들면 화면에서 몇 픽셀이다.** 600mm 타일 위의 120mm 상자는 타일의 1/5 이고,
기본 진입 카메라에서 랙(2m)과 함께 잡히면 사실상 점이다. 모델을 정교하게 만들어도 안 보인다.

그러므로 이 4종은 **실측 치수보다 "얼마나 키울지"가 먼저다.** 선택지:

1. **실측 그대로.** 정직하지만 안 보인다. 색 박스보다 오히려 못하다(색 박스는 0.2~0.3m 였다).
2. **알아볼 수 있는 크기로 확대**(예: 최장변 0.3~0.4m). 형상은 실물 비율을 지키되 통째로 키운다.
   ✅ 권장 — 이 오브젝트들의 목적이 "여기 이런 설비가 있다"를 알리는 것이지 치수 전달이 아니다.
   기존 색 박스도 같은 이유로 임의 높이를 썼다(`LAYOUT_OBJECT_HEIGHTS_M` 주석).
3. 실측 크기 + 바닥에 눈에 띄는 마커. 오브젝트가 둘로 늘어 화면이 복잡해진다.

§4-B 에서 확정한 "기둥 없이 1.2~1.5m 에 띄운다"와 함께 적용한다 — 띄우면 랙에 가리지 않아
확대 폭을 덜 잡아도 된다.
